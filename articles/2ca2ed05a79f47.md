## なぜキャッシュ API がアップデートされたのか

Next.js 16 では Partial Pre-Rendering や Cache Components が正式な開発モデルになり、キャッシュの整合性をより明確に制御する必要が出てきました。従来の`revalidateTag()`は万能な無効化フックでしたが、即時整合性が必要なフォームなどでは扱いづらい場面もありました。今回のリリースでは、SWR を前提とした`revalidateTag()`の振る舞いが再整理され、Server Action 専用の`updateTag()`が追加されたことで、静的最適化とリアルタイム性の両立がしやすくなっています。

## revalidateTag()の主な変更点

- **第 2 引数が必須**: `revalidateTag(tag, cacheLifeProfile)`に統一され、再検証ポリシーを明示しないと警告が出ます。
- **cacheLife プロファイル**: `'max'`, `'hours'`, `'days'`などのビルトイン、または`next.config.ts`で定義したカスタムプロファイルを渡して SWR の期限を制御します。インラインで`{ expire: 3600 }`のようなオブジェクトも指定可能です。
- **用途の限定**: キャッシュを即座に破棄するのではなく「古いデータを返しつつ裏で再取得」が前提になりました。ユーザー操作直後の即時反映には向きません。

| ユースケース       | 推奨プロファイル | 効果                                         |
| ------------------ | ---------------- | -------------------------------------------- |
| 記事・ドキュメント | `'max'`          | 長寿命キャッシュ。即レスポンス＋裏で再取得。 |
| ニュースフィード   | `'hours'`        | 数時間ごとの自然な再取得。                   |
| カスタム API       | `{ expire: 60 }` | 任意秒数で細かくリフレッシュ。               |

```ts
import { revalidateTag } from "next/cache";

export async function POST() {
  // CMSのWebhookを処理
  await revalidateTag("blog-posts", "max");
  return Response.json({ ok: true });
}
```

## updateTag()とは

`updateTag()`は Next.js 16 で追加された Server Action 専用 API です。同じリクエスト内でタグ付きキャッシュを即座に期限切れにし、後続の`fetch`や Cache Component が「書き込み直後の値」を必ず読むようにします。ユーザー設定フォームやコメント投稿のように、送信直後に結果が変わるべき UI で威力を発揮します。

```ts
"use server";
import { updateTag } from "next/cache";

export async function updateUser(userId: string, input: UserInput) {
  await db.user.update(userId, input);
  // user-<id>タグを再取得させることで即座に最新状態を反映
  updateTag(`user-${userId}`);
}
```

> ⚠️ Server Action 以外（Route Handler や Edge Runtime など）からは呼び出せません。あらかじめ`fetch()`や Cache Component にタグを付けていないと効果が出ない点にも注意します。

## revalidateTag と updateTag の比較

| 観点               | revalidateTag                                  | updateTag                                        |
| ------------------ | ---------------------------------------------- | ------------------------------------------------ |
| 一貫性             | SWR: 古いデータを返しつつ裏で更新              | Read-your-writes: リクエスト内で即最新           |
| 主な用途           | Webhook 連携、段階的に更新される静的ページ     | フォーム送信、設定変更、ライブ編集               |
| 呼び出し可能な場所 | Route Handler・Server Action                   | Server Action のみ                               |
| 引数               | `tag`, `cacheLife`プロファイル                 | `tag`のみ                                        |
| 影響範囲           | タグに紐づくキャッシュを期限切れにし再フェッチ | タグを即時更新し同リクエスト内の読み込みにも反映 |

## 実践シナリオ

- **設定フォーム**: Server Action で DB 更新後に`updateTag('user-<id>')`、Account ページヘッダーやプロフィールカードを即時更新。
- **CMS Webhook**: Route Handler から`revalidateTag('blog-posts', 'max')`を呼び、既存の静的ページを安全に SWR。
- **コメント欄 ×SWR**: 投稿直後は`updateTag('comments')`で本人の結果を即反映し、深夜バッチでは`revalidateTag('comments', 'hours')`で全体を再取得。

## よくある落とし穴

- タグ未設定の`fetch()`ではどちらの API も効果なし。`next: { tags: [...] }`や Cache Component の`tags`オプションを忘れずに。
- `updateTag`を Route Handler で呼ぶとビルドエラー。Server Action に処理を寄せるか、`revalidateTag`へ置き換えが必要。
- 旧シグネチャ`revalidateTag('tag')`は Next.js 16 で警告となり、将来削除予定。
- 同期的な`cookies()`や`headers()`と同様に、`updateTag`も非同期 Server Action 内でのみ利用可能。クライアントコンポーネントからは`useTransition`＋ Server Action で呼び出す。

## 移行チェックリスト

1. 既存コードから`revalidateTag`の呼び出しを洗い出し、第二引数の`cacheLife`プロファイルを追加する。
2. フォーム送信・設定変更など即時反映が必要な箇所を Server Action 化し、`updateTag`に置き換える。
3. `fetch()`に付けるタグの命名規約（例: `resource:<id>`）をチームで統一し、Cache Component でも再利用する。
4. `next.config.ts`で再利用する`cacheLife`プロファイルを定義し、魔法の数字を排除する。
5. 「書き込み → 再読み込み」の E2E テストを用意し、updateTag/revalidateTag の使い分けが崩れていないか自動検証する。
